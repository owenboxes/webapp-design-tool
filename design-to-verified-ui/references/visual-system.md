# 시각 디자인 기준 (visual-system v0.1)

`philosophy.md`가 "무엇을 보여 주나"라면 이 문서는 "어떻게 보이게 하나"다. 철학과 따로 관리한다(DECISIONS 2026-11-11).
수치는 토스 웹 실측(collab/notes/19)에서 **구조만** 가져왔고 색은 따로 정했다. 실제 서비스의 색·로고·글꼴·그림을 그대로 쓰지 않는다.

- 언제 읽나: SKILL.md 0단계(색·분위기 묻기), 1단계(역할 토큰), 2단계(구현), 4단계(리뷰)
- 판정: 이 문서의 수치 규칙은 아직 **[측정]** — 값을 기록하고 리뷰 의견으로만 쓴다. 대비(4.5:1·3:1)만 기존 [확정] 규칙(checklist §7)이다.

## 1. 적용 범위
- **과업 화면**(입력·목록·확인·결제·설정·검색 결과): §3~§5를 따른다.
- **보여 주는 면**(대표 이미지, 앨범·표지 그림, 첫 화면 대표 영역): 분위기(§2)에 따라 자유롭게. 글자는 그림 위에 바로 올리지 않고 단색 면 위에 둔다. 올려야 하면 아래에 어두운 면을 깔고 대비를 잰다.
- 마케팅·랜딩 페이지 연출은 범위 밖.

## 2. 색과 분위기 정하기
### 2-1. 묻기 (0단계)
사용자가 색·분위기를 말하지 않았으면 0단계 질문에 함께 묻는다: "원하는 분위기(예: 차분 / 화려 / 따뜻 / 신뢰)나 브랜드 색이 있나요?"

### 2-2. 색상 코드로 제안하기
명확한 색상 코드(#RRGGBB)가 없으면 **입력된 말에서 추론해 구체 코드로 제안**한다. 말만 받아 적지 않는다.
1. 입력을 해석해 적는다. 예: "믿음직하고 빠른 느낌" → 차가운 계열, 채도 중간, 강조색은 파랑~남색.
2. §2-4 표의 역할마다 코드를 정한다. 강조색은 1개.
3. 모든 글자·배경 조합의 대비를 계산해 표로 붙인다. 4.5:1(큰 글자 3:1), 입력칸 경계 3:1에 못 미치면 명도를 조정한 값으로 바꾸고 원래 값을 함께 적는다.
4. 설계 문서 "색 제안" 절에 `입력 → 해석 → 코드 → 대비` 순으로 남기고, 대화형이면 사용자에게 보여 주고 확인을 받는다.
5. 대화형이 아닌 실행이면 기다리지 않고 제안값으로 진행하며 "추론값 사용(확인 필요)"이라고 표시한다.
- 사용자가 코드를 줬는데 대비가 부족하면 그 코드를 장식·큰 면에만 쓰고, 글자·버튼용으로 보정한 값을 따로 제안한다.
- 특정 실제 서비스를 참고로 말해도 그 서비스의 고유 색을 그대로 쓰지 않는다. 구조(회색 단계, 강조 1개 등)만 참고한다.

### 2-3. 분위기 변형
| 분위기 | 바탕 | 강조 | 보여 주는 면 | 어울리는 예 |
|---|---|---|---|---|
| 차분 | 연회색 바탕 + 흰 카드 | 차가운 색 1개 | 없음 또는 작은 단색 아이콘 | 가계부, 설정, 업무 |
| 화려 | 어두운 바탕 + 한 단계 밝은 면 | 밝은 색 1개(버튼 글자는 어두운 색) | 생성한 SVG·그라데이션 그림을 카드·대표 영역에만 | 음악, 영상, 게임 |
| 따뜻 | 미색 바탕 + 흰 카드 | 따뜻한 색 1개 | 표지·사진 중심 | 서점, 생활, 음식 |
| 신뢰 | 흰 바탕 + 아주 연한 회색 구획 | 짙은 파랑·남색 1개 | 거의 없음, 숫자·표가 주인공 | 금융, 검색, 공공 |

분위기가 바뀌어도 글자 단계·간격·모양(§3~§5)은 같다. 바뀌는 것은 색과 보여 주는 면뿐이다.

## 3. 글자
- 글꼴: `"Pretendard Variable", Pretendard, -apple-system, BlinkMacSystemFont, system-ui, "Apple SD Gothic Neo", "Noto Sans KR", "Malgun Gothic", sans-serif`
  - Pretendard(SIL OFL) CDN: `https://cdn.jsdelivr.net/gh/orioncactus/pretendard@v1.3.9/dist/web/variable/pretendardvariable-dynamic-subset.min.css`. 대안: SUIT(OFL).
  - **font-family에 이름만 적으면 글꼴이 바뀌지 않는다.** HTML `<head>`에 위 CSS를 `<link rel="stylesheet">`로 실제로 넣는다. 넣지 못했거나 네트워크가 없으면 보고서에 "시스템 글꼴로 대체"라고 적는다. 검증 때 `document.fonts.check('16px "Pretendard Variable"')` 같은 방법으로 적용 여부를 확인할 수 있다.
  - 실제 서비스 전용 글꼴(예: Toss Product Sans)은 쓰지 않는다.
- 크기 단계 [측정 — 단계 밖 값의 수를 기록]:

| 단계 | 모바일 | PC | 줄 간격 | 굵기 |
|---|---|---|---|---|
| 큰 숫자(금액·핵심 상태) | 28 | 32 | 1.3 | 700 |
| 화면 제목 | 22 | 26 | 1.35 | 700 |
| 섹션 제목 | 18 | 20 | 1.4 | 700 |
| 강조 본문·라벨 | 16 | 16 | 1.5 | 600 |
| 본문 | 15 | 16 | 1.55 | 400~500 |
| 설명·캡션 | 13 | 14 | 1.5 | 400 |
| 배지 | 12 | 12 | 1.35 | 600 |

- 11px는 시간·출처·배지 같은 보조 정보에 써도 된다(2026-11-11 OWEN 확인: 읽기에 지장 없고 필요한 정보). 본문·버튼·입력 라벨은 13px 이상. 11px보다 작은 글자 [측정 — 개수 기록].
- 숫자·금액: `font-variant-numeric: tabular-nums`. "원"은 숫자와 같은 줄에, 같거나 한 단계 작게.
- 제목 자간 약 −0.4px, 본문 0.

## 4. 간격·모양
- 간격 단위 4px: 4·8·12·16·20·24·32·40·56·80 [측정 — 단계 밖 값 기록].
- 화면 좌우 여백: 모바일 20px(최소 16px). PC 과업 화면은 본문 폭 640~720px 가운데, 목록·격자·검색 결과는 최대 1120px.
- 섹션 간격: 모바일 32px, PC 48~80px. 카드 안쪽: 모바일 20px, PC 24px.
- 가로 스크롤 목록: 첫 항목은 섹션 제목과 같은 선에서 시작, 끝에도 같은 여백(`scroll-padding`). 오른쪽 항목을 일부 보여 더 있음을 알린다.
- 모서리: 배지 6 · 버튼·입력칸 12 · 카드 16 · 시트·팝업 24 · 알약 9999.
- 높이: 하단 고정 주요 버튼 52, 일반 주요 버튼 48, 보조 버튼 40, 입력칸 48, 목록 행 최소 56. 터치 대상 44px 권장, 24px 미만 실패(기존 [확정]).
- **포커스 표시**: 묶음 입력(둥근 검색창처럼 틀 안에 입력칸·버튼이 있는 것)은 바깥 틀 하나에만 포커스 표시를 준다. 안쪽 `input`은 `outline: none; border: 0`으로 사각 테두리를 없애고, 틀에 `:focus-within`으로 강조색 테두리(또는 2px 링)를 준다. 포커스 표시를 아예 없애지 않는다(WCAG 2.4.7). 단독 버튼·링크는 `:focus-visible` 2px 강조색 링.
- 그림자: 기본은 쓰지 않고 면 색 차이 + 구분선. 떠 있는 것(하단 고정 바, 시트, 메뉴)만 `0 4px 16px rgba(20,24,34,.08)`.

## 5. 움직임
- 과업 화면 전환·펼침 150~250ms, `cubic-bezier(.2,0,0,1)`. 300ms 넘는 연출은 과업 흐름에 쓰지 않는다 [측정].
- 눌림 피드백: 배경을 한 단계 진하게.
- `prefers-reduced-motion: reduce`이면 이동·확대 연출을 없애고 즉시 전환 (V21).
- 스크롤에 묶인 연출, 자동으로 넘어가는 슬라이드는 과업 화면에 쓰지 않는다.

## 6. 아이콘·그림·글꼴 소스 (라이선스 확인된 것)
- 아이콘: Lucide(ISC), Tabler Icons(MIT). 2D 단색 선 아이콘, 한 화면에 한 세트.
- 그림: 외부 이미지 대신 직접 만든 SVG·CSS 그림. 실제 브랜드 로고·캐릭터·서비스 고유 그림 금지.
- 글꼴: Pretendard, SUIT (모두 SIL OFL).

## 7. 다른 디자인 스킬과 함께 쓸 때
- 과업 화면의 정보 구조·글자 단계·대비·간격은 이 문서와 philosophy.md가 우선한다.
- frontend-design 같은 스킬은 분위기와 "보여 주는 면"(그림 방향, 강조색 성격)에만 참고한다.
