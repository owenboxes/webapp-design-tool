# design-to-verified-ui

웹앱 화면을 **설계 → 구현 → 브라우저 검증 → 수정 → 재검증**까지 끝내는 스킬이다.
디자인 판단 기준은 `references/philosophy.md`(v0.5) 하나다. 이 파일은 작업 순서와 꼭 지킬 규칙만 담는다.

## 한 문장
**사용자가 판단해야 할 것을 줄이되, 알아야 할 것은 숨기지 않는다.**

## 언제 쓰나
- 웹앱 화면·흐름을 새로 만들거나 고칠 때 (폼, 목록, 대시보드, 단계형 흐름, 결제·구독·해지·동의·삭제 화면)
- 기존 화면을 디자인 리뷰할 때 (이 경우 0~2단계와 5단계만 수행하고 구현은 제안으로 남긴다)
- 쓰지 않는 경우: 마케팅 랜딩 페이지의 연출 중심 작업, 네이티브 앱, 인쇄물

## 작업 순서

### 0. 입력 받기
시작할 때 아래를 **한 번에** 묻는다. 답이 없거나, 대화형이 아닌 실행(자동화·다른 에이전트의 요청·"바로 만들어 줘")이면 **기다리지 말고 대체값으로 진행**하고 산출물에 "대체값 사용"이라고 적는다. 답이 나중에 오면 그때 반영한다.

| 입력 | 없을 때 대체값 |
|---|---|
| 브랜드 색·분위기·참고 서비스 | **반드시 묻는다.** 색상 코드가 없으면 입력된 말에서 추론해 **구체 색상 코드로 제안**한다(`references/visual-system.md` §2). 대화형이 아니면 추론값으로 진행하고 "추론값 사용(확인 필요)" 표시 |
| 전하고 싶은 감정 1개 (예: 안심, 성취, 가벼움) | 과업 성격에서 추정하고 추정임을 표시 |
| 문구 어조 (해요체 / 합쇼체 등) | 해요체. 공공·금융·법률 안내처럼 격식이 어울리면 대화형일 때 확인. 정한 어조는 사이트 전체에 통일 |
| 사용 맥락 (기기·장소·자세·시간 압박·숙련도) | 모바일, 짧은 시간, 일반 사용자로 가정하고 표시 |
| 실제 데이터·조건 (금액, 기간, 환불·위약금 규칙) | 가상 데이터임을 화면과 문서에 표시. 실제 조건을 지어내지 않는다 |

기본값(DECISIONS 확정): 문구 어조는 **해요체**(사이트 성격·사용자 요청에 따라 변경 가능, 통일은 필수), **모바일 우선**(390px 설계 → 1440px 확장), **WCAG 2.2 AA**.

### 산출물 위치 (프로젝트에 정해진 규칙이 없을 때)
| 산출물 | 기능·예제 폴더 하나일 때 | 문서 폴더가 따로 있을 때 |
|---|---|---|
| 설계 문서 (1단계) | `<기능 폴더>/README.md` | `docs/DESIGN.md` (기능이 여럿이면 `docs/design/<기능>.md`) |
| 검증 보고 (5단계) | `<기능 폴더>/REVIEW.md` | `docs/VERIFICATION.md` |
| 스크린샷·원본 결과·검증 스크립트 | `<기능 폴더>/verification/` | `docs/verification/` |
프로젝트에 이미 문서 규칙이 있으면 그것을 따르고, 고른 위치를 보고에 적는다.

### 1. 설계 문서 먼저
코드를 쓰기 전에 `references/templates.md`의 설계 문서를 채운다. 최소 항목:
1. 사용 맥락과 감정 1개
2. **화면 목록과 화면별 모드** — 판단 기준: "이 행동을 되돌릴 수 있는가?"
   - 되돌릴 수 있음 → **기본 모드**: 한 화면 한 결정, 주요 행동 1개
   - 되돌릴 수 없음, 또는 비용·위험·법적 조건 → **번역 모드**: 지우지 않고 쉬운 말로 풀어 전부 보인다
   - 기간 안에 취소할 수 있는 행동(해지 예약, 주문 취소 요청 등)은 "되돌릴 수 있음". 조건 안내는 번역 모드로 하되 실행 후 "○○ 예정" 상태와 취소 경로를 남긴다
3. 여정 단계 수 (개선 작업이면 전후 비교)
4. 화면별 상태: 기본·로딩·오류·빈 상태(+ 되돌릴 수 없는 작업은 처리 중/완료 구분)
5. **번역 모드 화면마다 상태별 조건 문구 표 — 빠뜨리면 실패.** 먼저 "이 행동 직전에 사용자가 어떤 상태일 수 있나"를 나열한다.
   - 예: 구독 해지 — 결제 전 / 이용 중 / 해지 예정마다 청구액·이용 종료·환불·취소 기한
   - 예: 계정·데이터 삭제 — 내보내기 안 함 / 일부만 내보냄 / 전부 내보냄마다 "잃게 되는 것"과 "삭제 전에 내려받기" 경로
   - 예: 결제·송금 — 첫 결제 / 정기 결제 중 / 잔액 부족마다 청구 시점·금액·실패 시 처리
6. 제품 용어집 (같은 대상은 같은 단어)
7. 색 제안(입력 → 해석 → 코드 → 대비 표)과 역할 토큰(색·글자 단계·간격) — `references/visual-system.md`

### 2. 구현
`references/philosophy.md` §1~§4와 `references/visual-system.md`(글자 단계·간격·모양·움직임)를 따른다. 특히 자주 틀리는 규칙:
- **첫 줄은 정보.** 사용자가 확인하러 온 값(금액·상태·다음 행동)이 가장 먼저, 가장 크게. 영문 장식 머리말("YOUR MONTH…") 금지.
- **입력이 과업인 첫 화면(검색·로그인 등)은 입력창이 첫 줄이다.** 머리글 바로 아래에 입력창. 그 위에 슬로건·서비스 소개·환영 문구를 두지 않는다. 이 스킬의 철학 문장을 화면 문구로 옮기지 않는다.
- **어조는 하나로.** 확인 질문("삭제할까요?")·빈 상태("없어요")·오류까지 정한 어조로 통일한다. "~하시겠습니까", "~없습니다"가 해요체 화면에 섞이기 쉽다.
- **입력창 안내 문구는 잘리지 않게.** 좁은 폭에서 "(예: …)"가 잘리면 예시를 뺀 짧은 문구로 바꾼다. 화면 폭이 아니라 입력칸에 실제로 들어가는지 재서 고르고, 크기가 바뀌면 다시 잰다. 짧은 문구도 안 들어가는 칸(좁은 머리글 검색창 등)은 "검색"처럼 한 단계 더 줄이고, 320px에서 확인한다.
- **뜻 없는 기호·문구 금지.** 아이콘·기호는 뜻과 맞게(돈과 무관한 곳에 `$` 금지), 근거 없는 수치·무슨 기능인지 모를 라벨을 쓰지 않는다. 애매하면 글자로만.
- **과업 화면(설정·목록·폼·확인)의 장식 문구는 정보 아래로 내리거나 뺀다.** 슬로건, 섹션 옆 부제("쌓아온 기록을 내 손에"), 감성 소개("나의 일상을 차곡차곡…"), 정보 없는 일러스트가 화면 위쪽을 차지하면 안 된다(원칙 6 "더하기보다 뺀다": 새 요소는 근거가 있을 때만). 브랜드 감정은 완료·빈 상태·첫 사용 같은 순간에 담는다(원칙 10).
- **단계 화면 하단 행동은 최대 2개**(주요 1 + 보조 1). 되돌리기는 상단 "← 이전" + 흐름을 닫는 "닫기(○○ 취소)" 하나. 선택지마다 "선택 취소"를 붙이지 않는다. "건너뛰기"는 온보딩·선택 사항 안내에만.
- **진행 표시는 사실.** n/N의 N은 확인·동의 화면을 포함한 실제 화면 수. 내비 활성 표시와 `aria-current`는 실제 위치와 일치.
- **누를 수 있어 보이는 모양은 누를 수 있는 것에만.** 화살표·밑줄·알약 테두리·손가락 커서는 실제 동작 요소에만. 버튼 이름 = 누른 결과.
- **되돌릴 수 없는 행동 안내는 위험에 맞춘다.** 검색 기록 비우기처럼 잃는 것이 작으면 "(복구 불가)" 짧은 표기 하나. 돈·계정·사용자 콘텐츠는 번역 모드 전체.
- **번역 모드의 핵심 조건**(금액·기간·위험·취소 방법)은 접기 안에만 두지 않는다. 원문은 접어도 된다. 조건 문구는 사용자 상태로 계산한다 — **틀린 안심 문구는 숨기는 것보다 나쁘다.**
- **로딩 화면의 할 일은 "기다리기"다.** 로딩 중에 눈에 띄는 주요 버튼을 두지 않는다. 탈출구가 필요하면 보조 텍스트 버튼 하나. "다시 시도"는 오류 상태의 행동이다.
- "○○ 예정" 항목은 **목록에서도** 배지 등으로 구분하고 취소 기한(이용 중이면 이용 종료일도)을 보인다.
- 피드백 알림은 콘텐츠를 가리지 않게 문서 흐름 안에. 방금 바뀐 항목은 목록에서 구분해 보인다.
- 효과보다 읽힘: 블러·투명·그라데이션 위 텍스트도 기본 상태에서 대비 기준 충족. 유리 효과는 내비게이션 레이어에만. 과업 화면에 스크롤 연동 연출 금지.
- 라이팅: 버튼은 행동으로("결제하기"), 흐름 라벨 통일(시작하기 → 다음 → 결과 라벨), "우리" 주어·감탄사·"여기를 클릭" 금지, 오류는 문제 옆에 고치는 방법으로, 빈 화면엔 다음 행동.

### 3. 브라우저 검증
`references/verification.md`를 따른다. 핵심:
- **정상 HTTP 주소**로 띄워서 본다(HTML 직접 주입·파일 열기만으로 통과 처리 금지).
- 390px와 1440px 두 폭 × 모든 주요 화면 × 상태(기본·로딩·오류·빈·해당 시 처리 중/완료).
- 자동: 가로 넘침, 텍스트 대비, 24×24px 미만 컨트롤, 콘솔 오류·요청 실패, 핵심 흐름 조작(앞으로·이전·닫기·실행·취소·새로고침 후 유지), 키보드 포커스, 글자 크기 단계(`scripts/ui-checks.cjs`의 `measurePage(page, {enforceScale:true})` — 합친 단계 밖·11px 미만이면 실패, 간격은 기록만).
- **검사기를 믿기 전에 일부러 깨 본다**: 넘침·무반응 버튼·로딩 고착 같은 결함을 넣었을 때 실패하는지 확인한다.
- 스크린샷을 남기고 **직접 눈으로 본다.** 자동 통과는 디자인 통과가 아니다.

### 4. 수정과 재검증
- `references/checklist.md`로 수동 리뷰를 하고, 발견한 결함을 고친 뒤 **같은 검증을 다시 실행**한다.
- 고치기 전에 해당 검사가 실패하는 것을 먼저 확인하면 좋다(수정 전 실패 → 수정 후 통과).

### 5. 보고
`references/templates.md`의 보고 형식으로 남긴다.
- 결과는 **통과 / 실패 / 미수행 / 해당 없음 / 지원 불가** 중 하나. **실행하지 않은 검사에 통과 표시 금지.** 미수행은 이유를 적는다. 측정 대상이 0개였던 검사도 통과가 아니다.
- 검사 범위를 실제보다 넓게 쓰지 않는다 (예: "1440px에서만 실행"이면 그렇게 적는다).
- 자동 검사 결과와 디자인 리뷰 결과를 섞지 않는다.
- **수동 리뷰를 "통과"로 적을 때는 근거를 함께 적는다**(확인한 문구 예시, 측정값, 화면 파일). 근거 없이 "해요체 적용", "6단계 사용"처럼 쓰지 않는다.
- 실행 환경(도구·브라우저 버전), 명령, 종료 코드, 증거 파일 경로.
- **넘긴 뒤 다시 확인할 항목**: 문구·금액 변경, 스타일 변경, 동작·저장 변경, 의존성 변경 각각에 대해 재검증할 화면과 명령.

## 무엇이 실패이고 무엇이 아닌가
판정 기준은 `references/checklist.md`의 표시 하나로 통일한다.
- **[확정]** — 위반이면 실패. checklist.md에 [확정]으로 표시된 **모든** 항목이 해당한다. 대표 예:
  - 단계 화면 하단 행동 ≤ 2, 선택 취소·불필요한 건너뛰기 없음
  - WCAG 2.2 AA (텍스트 대비 4.5:1, 큰 글자 3:1, 키보드 조작·포커스 표시, 터치 영역 24×24px **미만이면 실패** — 44×44px는 권장일 뿐)
  - 진행 표시 N = 실제 화면 수, 내비 활성 표시 일치
  - 번역 모드 핵심 조건이 접기 안에만 있지 않음, 상태별 조건 문구 표 존재
  - 버튼 이름 = 누른 결과, 비대화형 요소에 누를 수 있어 보이는 모양 없음, 영문 장식 머리말 없음
  - 입력이 과업인 첫 화면의 입력창 위 슬로건 없음, 정한 어조 통일, 되돌릴 수 없는 행동의 "복구 불가" 표기, 뜻과 맞지 않는 기호·근거 없는 수치 없음 (v0.5)
  - 글자 크기는 모바일·PC 단계를 합친 값(11~32px 12개) 안, 11px 미만 없음 (V28)
- **[측정]** — 수치 임계값(화면당 주요 행동 수 상한, 글자 스타일 수 상한 등)은 **미확정**이다. 값과 리뷰 의견만 기록하고 실패 처리하지 않는다.
- **[후보]** — 리뷰에서 나왔지만 철학에 아직 없는 규칙. 리뷰 의견으로만 남긴다.
